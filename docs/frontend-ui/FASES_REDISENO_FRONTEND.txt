1. CONCLUSIÓN DEL ANÁLISIS
========================
Sí podemos empezar. El kit ya define una dirección visual suficiente, pero no
conviene cambiar todas las pantallas a la vez ni limitarse a sustituir colores.
Primero se construyen los componentes compartidos; después se valida la nueva
interfaz con el flujo financiero y se extiende al resto de la aplicación.

La personalidad viajera se concentrará en marca, títulos, ilustraciones y pequeños
detalles. Los importes, formularios, permisos y estados de pago deben conservar una
lectura directa. No agregaremos reservas, vuelos, hoteles, propuestas ni votaciones.
Un gasto seguirá pudiendo existir sin actividad de itinerario asociada.

Este análisis se basa en rutas, páginas, componentes, estilos, servicios, hooks,
tipos y documentación locales. Incluye compilación y lint, pero no es una prueba
completa de interacción con cuentas reales ni una auditoría visual de cada estado.
Antes de dar por terminada cada fase se probará en navegador con backend y usuarios
de prueba. La vista local sin servicios reales no certifica los flujos financieros.

2. LO QUE EXISTE Y LO QUE DEBEMOS ATENDER
======================================
- Stack verificado: React 19, TypeScript, Vite, Tailwind CSS 3, React Router,
  Recharts, Supabase y Socket.IO. No hace falta cambiar de framework para renovar UI.
- Hay 14 rutas específicas y una ruta comodín de error (15 páginas). Finanzas, Itinerario y
  Archivos están dentro de DashboardPage; no son tres páginas independientes.
- La identidad actual conserva morados, verdes y colores hexadecimales directos.
  index.css y tailwind.config.js usan Plus Jakarta Sans y DM Sans; el kit propone
  Fredoka y Nunito. Cambiar solo Tailwind dejaría muchos estilos antiguos intactos.
- Ya existen Button, Input, Card, Badge, Table, Avatar, Toast, ConfirmDialog y
  HelpButton, pero hay numerosos botones, campos y diálogos escritos por separado.
  Se deben reutilizar y completar estas piezas, evitando crear otro sistema paralelo.
- Button e Input tienen tamaños de 32/40/48 px. Adoptaremos 44 px como objetivo
  mínimo de área interactiva para uso táctil, sin agrandar indiscriminadamente todo.
- ConfirmDialog ya declara role y aria-modal, pero no implementa dentro del
  componente confinamiento/restauración del foco ni Escape. Tener ARIA no basta.
- MyWalletView contiene formularios con campos identificados solo por placeholder;
  hacen falta etiquetas persistentes y errores dentro del diálogo correspondiente.
- DashboardPage tiene 1,995 líneas; GroupPanelPage, 1,538; CreateGroupPage, 1,346;
  ProfilePage, 1,046. Hay que extraer secciones por responsabilidad al intervenirlas,
  conservando primero sus contratos. El tamaño no demuestra un fallo por sí solo.
- AppLayout combina altura de pantalla, scroll interno, sidebar de 256 px y panel
  derecho de 280 px. Revisar móvil, zoom, teclado virtual y modales será esencial.
- El logo del componente Logo.tsx es una composición temporal; debe migrar a los
  recursos del kit. Los PNG originales requieren verificar legibilidad en pequeño;
  una versión vectorial limpia es una mejora posterior, no un bloqueo inicial.
- Hay formatos monetarios inconsistentes: BudgetDashboard muestra algunas cifras
  sin decimales y BudgetSummaryPanel permite dos. ExpenseDraftForm redondea cifras
  en un mensaje de reparto. Definir presentación común sin modificar los cálculos.
- Hay datos de caché local y refrescos por Socket.IO. Cambiar de viaje o de sesión
  debe evitar mostrar datos del contexto anterior. Se requiere prueba específica;
  no se afirma aquí que exista una fuga de datos comprobada.
- Hay alertas nativas en la exportación del itinerario y mensajes técnicos para
  usuarios finales. Sustituirlos por feedback contextual y lenguaje claro.
- El contrato financiero actual declara reparto equitativo o personalizado. No
  presentar un modo porcentual nuevo como existente sin validar soporte del servidor.

Verificaciones ejecutadas sobre la base actual:
- npm run build: correcto.
- npm run lint: correcto.
- Advertencia de bundle: JS principal de aproximadamente 1,298.14 kB minificado
  (350.49 kB gzip), superior a la advertencia de 500 kB de Vite.
- Advertencia de datos Browserslist antiguos. Actualizarlos en un cambio técnico
  separado, comprobando el lockfile; no es necesario para incorporar este kit.
- No se encontró una suite frontend propia por nombres test/spec ni un script test
  en su package.json. Build y lint no sustituyen pruebas de uso.

- Archivos: selección, subida, fallo, descarga y vínculo parcial.
- Vacíos distintos de fallos; datos guardados frente a copia local desactualizada.
- Reglas para textos largos, monedas, decimales, fechas y contenido de ejemplo.

Los tokens del kit son la referencia visual. El HTML contiene ejemplos conceptuales;
no se debe copiar su simulación de guardado a los flujos de la aplicación.

7. CRITERIOS DE NIELSEN APLICADOS A CADA ENTREGA
=============================================
1) Visibilidad: indicar guardando, actualizado, pendiente y fallo con texto.
2) Lenguaje cotidiano: “Pagó”, “Te deben”, “Debes”, “Registrar pago”; moneda visible.
3) Control: cancelar, volver y corregir; confirmar acciones irreversibles.
4) Consistencia: mismo componente, verbo y ubicación para una misma acción.
5) Prevención: validar importes/repartos/fechas; impedir envíos repetidos.
6) Reconocimiento: nombres y contexto visibles; no depender de memorizar IDs.
7) Eficiencia: teclado, filtros y acceso directo a funciones frecuentes.
8) Claridad visual: cifras y siguiente acción primero; decoración secundaria.
9) Recuperación: explicar qué falló y cómo corregirlo conservando la captura.
10) Ayuda: aclarar reparto, presupuesto y confirmación del pago junto al control.

Esta lista es un criterio de revisión, no una certificación automática de usabilidad.
